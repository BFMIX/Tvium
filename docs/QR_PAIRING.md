# Local QR pairing

Native Tvium apps can receive a source from a phone when the TV has no convenient keyboard. On wide first-launch screens, pairing starts automatically and the QR code appears alongside manual source choices. Narrow phone screens show manual entry without starting a local listener. The TV binds a temporary HTTP listener to a private Wi-Fi or Ethernet IPv4 interface. VPN and virtual-adapter addresses are excluded because a nearby phone may not be able to reach them. If no suitable interface exists, the app shows a retry action.

Web builds, including Tesla, use a different path because a browser cannot accept inbound local connections. A hosted HTTPS relay must be configured at build time with `TVIUM_PAIRING_RELAY`. The Web option is shown only when that address is configured. The Netlify deployment in `services/metadata_gateway` serves the phone page and stores only the encrypted proposal. Published functions share a production store across deploys; previews use separate deploy stores. The functions allow the Tvium Pages origin. GitHub Pages alone cannot host the relay. Do not set the build variable to a placeholder or a service that is not running.

The QR contains a random 256-bit session token and a local address. It contains no playlist URL or provider credential. The listener closes after one valid submission, leaving onboarding, or ten minutes. After a phone submission, the receiving device starts import automatically and shows a success notice only after import succeeds. It does not show the URL or credentials in the status panel. The phone page and responses use no-store headers and contain no external scripts or analytics.

For native pairing, the phone submits details directly to the TV over local HTTP. This transfer is not encrypted; pair only on a trusted home network.

For Web pairing, the Web app creates a random 256-bit AES-GCM key. The QR fragment carries that key, a one-use submission token, and a session ID. The fragment is never sent to the relay in an HTTP request. The phone encrypts the source locally and submits only the nonce and ciphertext. The relay accepts the proposal during a ten-minute session; an hourly cleanup removes abandoned encrypted blobs. The receiving device decrypts locally and starts import. A separate viewer token lets it retrieve and delete the proposal. The relay must use HTTPS and avoid request-body and URL logging.

Synthetic tests cover token routing, expiration, single-submission behavior, adapter selection, input validation, encryption, and TV confirmation. The production Netlify relay at `https://tvium.netlify.app` passed synthetic create, submit, retrieve, replay rejection, delete, origin rejection, and cross-deploy persistence checks. The always-visible QR layout still needs physical-device review on Android TV, Tesla, and desktop after deployment.

## Existing phone playlist handoff (planned)

Scanning the QR currently opens a phone form for entering one M3U URL or one Xtream connection. It does **not** yet read playlists stored inside the iPhone or Android app. A browser page cannot access the app's secure local credentials. The second mode requires a native phone screen that scans or accepts the pairing link, lists existing sources, and asks which source to send. Transfer must be end-to-end encrypted even when the target TV uses a local HTTP listener. The target device must still confirm the source type before import. Do not describe this as account synchronization or copy the whole catalog; transfer one selected source configuration and let the target import locally.
