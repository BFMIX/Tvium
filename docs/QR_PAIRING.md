# Local QR pairing

Native Tvium apps can receive a source from a phone when the TV has no convenient keyboard. Pairing starts only after the user selects **Add with your phone** on the first-launch screen. The TV binds a temporary HTTP listener to a private Wi-Fi or Ethernet IPv4 interface and displays a QR code for that listener. VPN and virtual-adapter addresses are excluded because a nearby phone may not be able to reach them. If no suitable interface exists, the app asks the user to connect to a local network.

Web builds, including Tesla, use a different path because a browser cannot accept inbound local connections. A hosted HTTPS relay must be configured at build time with `TVIUM_PAIRING_RELAY`. The Web option is shown only when that address is configured. The Netlify deployment in `services/metadata_gateway` serves the phone page and stores only the encrypted proposal. Published functions share a production store across deploys; previews use separate deploy stores. The functions allow the Tvium Pages origin. GitHub Pages alone cannot host the relay. Do not set the build variable to a placeholder or a service that is not running.

The QR contains a random 256-bit session token and a local address. It contains no playlist URL or provider credential. The listener closes after one valid submission, cancellation, or ten minutes. The TV shows the submitted source type and requires confirmation before it imports the M3U URL or Xtream connection. It does not show the URL or credentials in that confirmation. The phone page and responses use no-store headers and contain no external scripts or analytics.

For native pairing, the phone submits details directly to the TV over local HTTP. This transfer is not encrypted; pair only on a trusted home network.

For Web pairing, the Web app creates a random 256-bit AES-GCM key. The QR fragment carries that key, a one-use submission token, and a session ID. The fragment is never sent to the relay in an HTTP request. The phone encrypts the source locally and submits only the nonce and ciphertext. The relay accepts the proposal during a ten-minute session; an hourly cleanup removes abandoned encrypted blobs. The TV decrypts locally, shows only the source type, and requires confirmation before import. A separate viewer token lets the TV retrieve and delete the proposal. The relay must use HTTPS and avoid request-body and URL logging.

Synthetic tests cover token routing, expiration, single-submission behavior, adapter selection, input validation, encryption, and TV confirmation. The production Netlify relay at `https://tvium.netlify.app` passed synthetic create, submit, retrieve, replay rejection, delete, origin rejection, and cross-deploy persistence checks. Android TV, Tesla, and other physical-device pairing still need runtime validation. The Web option appears in published builds only after the GitHub release uses that HTTPS origin.
